## 1. Propósito

O RMR-001 resolve o problema de **"onde mando uma adaptação/acoplagem futura sem decidir na hora se ela vira decisão, spec ou emenda?"**. Ele:

1. **Recebe** qualquer ideia/adaptação/acoplagem/módulo diferido em um único lugar (§5 Intake).
2. **Rastreia** cada item com um **Gatilho de Ativação** — a condição objetiva que define *quando* ele deve ser implementado (§3).
3. **Informa** — quando o gatilho dispara, o item passa a estado `ATIVADO` e o processo de gate é obrigado a tratá-lo (§4), de modo que nada "vencido" passe silenciosamente.
4. **Não duplica** os registros que já têm casa: decisões abertas (catálogo) e conformidade (CIC-001) são **indexadas** (§7), não copiadas.

## 2. Schema do item de backlog

Todo item tem os campos:

| Campo | Descrição |
|---|---|
| **ID** | `BL-nnn` (monotônico, nunca reusado — INV-07) |
| **Título** | Nome curto |
| **Tipo** | `Adaptação` · `Acoplagem` · `Ideia` · `Módulo diferido` |
| **Origem** | `arquivo:§/linha` onde o item nasceu |
| **Afeta** | Princípio(s) GPR-001 · Spec(s) · Trilha (A/B/ambas) |
| **Gatilho de Ativação** | A condição que torna o item "da hora" (§3) |
| **Ação ao ativar** | O que fazer quando o gatilho dispara (promover a decisão/spec/emenda/auditoria) |
| **Estado** | `Proposto` → `Em espera` → `ATIVADO` → `Absorvido` · ou `Descartado` (§ estados) |

**Estados (ciclo de vida — INV-07, nunca deleta):**
`Proposto` (registrado, aguarda validação) → `Em espera` (validado; gatilho ainda não disparou) → **`ATIVADO`** (gatilho disparou — **requer ação no próximo gate**) → `Absorvido` (implementado/incorporado; aponta para o artefato que o absorveu) · `Descartado` (com justificativa; permanece no registro histórico).

## 3. Modelo de Gatilho de Ativação

Cada item declara **um** gatilho objetivo e verificável:

| Prefixo | Significado | Exemplo |
|---|---|---|
| `spec:` | Ativa quando a Spec indicada é homologada (ou entra em redação) | `spec:SPEC-003 homologada` |
| `decisao:` | Ativa quando uma open decision é resolvida | `decisao:J-001 resolvida` |
| `milestone:` | Ativa ao concluir uma milestone do Road Map | `milestone:Fase 1 concluída` |
| `evento:` | Ativa por condição nomeada (ex.: saída do spec-only) | `evento:início da fase de implementação` |
| `hygiene:` | Ativa no próximo ciclo de Hygiene (PAP-001 Bloco 4) | `hygiene:próximo ciclo` |

Um item pode ter gatilho composto (`spec:SPEC-010 ∧ decisao:J-001`) — nesse caso só ativa quando **todas** as condições são verdadeiras.

**Re-apontamento de gatilhos (EUA-E21 / RULE-ECC-01).** As Specs futuras são *slots indicativos* definidos na abertura. Quando um slot que seja alvo de gatilho `spec:` for dividido, fundido, renumerado ou descartado: (a) o **Especificador** propõe o re-apontamento no Dossiê de abertura; (b) **Andraus** o homologa no mesmo ato da definição da Spec; (c) o **Controlador** o registra **aditivamente** neste painel (nota datada; o gatilho original é preservado — INV-07) no mesmo ato da DHR de abertura; (d) o **Revisor** confere a proposta no parecer. Gatilho para slot alterado **sem** re-apontamento homologado = **achado de gate** (§4). Itens com gatilho numérico hoje: BL-001, BL-002, BL-003, BL-004, BL-010, BL-011, BL-012, BL-013, BL-015, BL-016, BL-017.

## 4. Mecanismo "o sistema informa" (surfacing)

O repositório está em fase spec-only (ROADMAP §22) — não há runtime que dispare notificação. Portanto o "informar" é **garantido pelo processo de gate**, não por promessa:

1. **No gate entre Specs (ROADMAP §23) e no ciclo de Hygiene (PAP-001 Bloco 4):** é **obrigatório** consultar o RMR-001 e verificar quais itens tiveram o **gatilho disparado** desde o último gate (ex.: uma Spec recém-homologada satisfaz `spec:...`, uma decisão recém-resolvida satisfaz `decisao:...`).
2. Todo item cujo gatilho disparou vira `ATIVADO`. Um item `ATIVADO` **não tratado** é **achado de gate** (o Revisor o reporta; o gate não fecha limpo enquanto houver `ATIVADO` pendente sem encaminhamento).
3. A "Ação ao ativar" do item diz o que fazer: abrir a Spec, propor emenda, agendar auditoria, etc.

> **Wiring VINCULANTE** (homologado por DHR-PAP-001-C, 2026-09-19):
> - `ROADMAP.md §23` (gate entre Specs): passo **11-bis — Consultar RMR-001 / tratar itens ATIVADOS** (em vigor).
> - `PAP-001` Bloco 4 §6.3 (Ciclo de Hygiene): **consulta obrigatória ao RMR-001 e promoção dos ATIVADOS** (em vigor).
> Um item `ATIVADO` sem encaminhamento é **achado de gate** — o avanço não fecha limpo.
>
> **Automação futura (item BL-006):** um script de governança (`scripts/`) que, a cada homologação, varre os gatilhos e imprime os itens ATIVADOS — o "informar" automatizado. Não é código de runtime do SOT (não fere §22); ele mesmo está no backlog abaixo, ativado por `evento:existência de tooling de governança`.

## 4-bis. Vinculação automática por abertura de Spec (DHR-BACKLOG-ABERTURA-001, Andraus, chat 2026-10-12)

Todo item **não encerrado** cujo gatilho tem uma alternativa `spec:SPEC-nnn em redação` fica **VINCULADO à SPEC-nnn desde a abertura, por regra, sem depender de promoção de Andraus** — para ser objeto de especificação **em todo ou em parte, no que couber**.
- **Vincular ≠ promover ≠ absorver.** O Estado no painel **não muda** (`Em espera` permanece); `ATIVADO` e `Absorvido`/`Descartado` seguem homologados por Andraus (§5). O que muda: o item **não pode mais ficar sem tratamento** na Spec.
- O **Plan** da Spec DEVE declarar, na linha que cita cada BL vinculado, `Disposição: INCORPORADO` (todo) · `PARCIAL` (parte; dizer qual entra e qual não) · `REFERÊNCIA` (fonte de requisitos, sem absorver) · `FORA` — sempre com motivo. O Revisor audita o motivo; a **presença** é garantida por máquina.
- **Determinístico:** `python scripts/backlog_triggers.py --abertura SPEC-nnn` lista os itens (alcance `TOTAL` se a alternativa do gatilho é só a abertura; `PARCIAL` se há condição `∧` ainda não satisfeita); o gate `[STRUCT-13]` do `validate_spec_sot.py` reprova (fail-closed) o Plan sem disposição para algum deles; os hooks Stop/SubagentStop/SessionStart avisam (informativo) via `--abertura-pendentes`. Não retroage: Spec já homologada não é alcançada (INV-07).
- Gatilhos `milestone:`/`evento:`/`hygiene:`/`decisao:` **não** vinculam por abertura (dependem de julgamento — seguem §3/§4).

## 5. Protocolo de intake — "como enviar um item"

Para registrar uma adaptação/acoplagem/ideia futura:

1. Adicione uma linha no **Registro Vivo (§6)** com o próximo `BL-nnn`.
2. Preencha no mínimo: Título, Tipo, Origem (`arquivo:§`), Afeta, **Gatilho de Ativação**, Ação ao ativar. Estado inicial = `Proposto`.
3. Quem pode registrar: Especificador, Revisor, ou Andraus. Promoção `Proposto → Em espera` e `ATIVADO → Absorvido/Descartado` é homologada por Andraus (coerente com PC-08 e K-PAP-003).
4. Não resolva o item aqui — o RMR-001 só o **rastreia** até a hora; a implementação acontece na trilha/spec correspondente.
